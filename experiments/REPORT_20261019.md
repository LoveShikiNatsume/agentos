# OS2026 夜间实验与框架完善报告（2026-10-19）

2026-10-19 01:00 起自主推进，计划内的实验约 03:50 全部跑完并停掉 vLLM。只用服务器本地模型（RTX 4090，vLLM 0.26.0），没有调用 DeepSeek 等在线 API，没有 push。代码在个人副本 `/home/typemoon/agentos-private`（`main`），原始记录在服务器 `~/agentos-runs/`。

## 结论

1. 缓存亲和调度（实验 B）有了严格结论：收益只在 KV 容量放不下全部共享前缀时出现。容量充足时与普通顺序无差异（完工时间 −0.4%，95% CI [−2.1%, +1.2%]）；Qwen2.5-7B 把 KV 压到 750 块时，完工时间 −54.9% [−55.4%, −54.2%]，命中率 0.8% → 74.7%；Qwen3.5-9B 上 −51.0% [−51.3%, −50.7%]。任务完成时刻的 p50、p95 同时提前，没有出现饥饿。
2. 框架原来的自动策略在这种压力下没有收益：约 97% 的决策落到公平策略，因为饥饿阈值固定为 3000 ms，而一次 LLM 批处理约 2 s。新增按服务时间缩放的阈值和亲和老化上限后，自动策略的完工时间 −47.0% [−49.2%, −43.9%]，接近强制亲和；容量充足时不改变行为。
3. 按需装配（实验 A）重新设计：所需文档不再由实验预设，而由 planner 模型只看目录后声明。Qwen3.5-9B、100 道正式题：声明式装配的执行输入比广播全部候选少 88.1%，准确率 72.7% 对 66.7%，差 +6.1 个百分点 [−3.0, +15.2]，没有显著下降；同样文档预算的 BM25 检索准确率 48.5%，差 −18.2 个百分点 [−30.3, −5.1]。换 Qwen3.8-27B 复跑结论一致（declared −2.3 [−7.0, +2.3]，BM25 −39.5 [−50.0, −29.1]）。
4. 框架补了两块：LangGraph 静态图自动生成 TaskDAG 与 ACB；语义层容错（任务声明校验器，不通过时带反馈重试，可选快照恢复，检测重复结果与重复工具调用）。
5. 语义层容错（实验 C）：100 道题首轮都注入故障，带反馈重试把准确率从 0% 恢复到 87%–96%，语义注入全部被校验器发现。重试前快照恢复与保留残留相比，答案内容没有可测差别（Qwen3.5 −2 个百分点 [−9, +5]；Qwen3.8 严格判分 −8 [−15, −2]，但全部是答案被包进 Markdown 代码块的格式问题，去掉后都是 100%），输入只少 3%–4%。Qwen3.5 保留残留时有 2/50 道语义题照抄了残留的错误事实，被重复检测提前停止。这个任务的残留很短，对照区分度不够。

## 三、实验 A：按需装配（重新设计）

旧设计的问题：所需片段由实验脚本按角色预先固定，输入减少是写死的，不能说明 Runtime 能自己决定装配什么。

新设计（服务器 `experiments/context_selection/README.md`）：

- 题集：从 `/usr/lib/python3.11` 源码用 AST 生成 120 道可自动判分的题（20 道探测、100 道正式），每题比较 2–3 个函数的形参，8 个候选文档（其余为同模块、同定义类型或名称词重合的干扰项）；答案为严格 JSON，精确判分。
- 流程：planner 只看题面和候选目录（名称与符号，不看原文），输出 1–4 个 reader 及各自的 `context_refs`；计划冻结后四组共用。每题一张 TaskDAG，经过 `adapt_plan` → `Runtime.run`；reader 读原文抽取事实，answerer 汇总 reader 结果作答。
- 四组只改文档引用：`all` 广播全部 8 个候选；`declared` 用 planner 的声明；`bm25` 以 reader 目标检索，平均文档数与 declared 精确对齐；`oracle` 给全部所需文档（answerer 也看原文，作上限参照）。
- 参数：Qwen3.5-9B，关闭思考，温度 0，输出上限 4096，截断计无效。按题配对 bootstrap 95% CI。

Qwen3.5-9B，100 道正式题（各组 1 轮，截断 0；1 题 planner 失败，各组都计错）：

| 组 | 准确率（有效 99 题） | 每题执行输入 Token | 相对 all 的准确率差 [95% CI] | 输入变化 |
|---|---:|---:|---|---:|
| all | 66.7% | 46,211 | — | — |
| declared | 72.7% | 5,518 | +6.1 pp [−3.0, +15.2] | −88.1% |
| bm25 | 48.5% | 5,533 | −18.2 pp [−30.3, −5.1] | −88.0% |
| oracle | 65.7% | 16,808 | −1.0 pp [−9.1, +7.1] | −63.6% |

planner 共用一次，100 题合计 101 次调用、15.8 万输入 Token；计入后 declared 总输入为 all 的 14.9%。BM25 有 71 题漏掉所需文档，这些题准确率 38.0%，齐全的 28 题 75.0%。

解读与限制：

- 声明式装配在这组题上没有损失准确率，同预算的检索明显变差，说明收益来自“谁需要什么”的声明，而不是单纯少给。
- 题面直接点名了要比较的符号，planner 在 99/99 题都声明了完整的所需文档，声明难度低于真实任务。真实任务中声明会漏，这组数字是声明准确时的情形。
- Qwen3.5 上 all 比 declared 低，但 100 题下差值的 CI 跨 0，只能说没有下降。

换模型复跑：Qwen3.8-27B-AWQ-INT4，planner 与执行同模型，重新冻结计划。14 题的 planner 两次都把 JSON 包在 Markdown 代码块里，按协议判计划失败、各组计错，下表为其余 86 题：

| 组 | 准确率（有效 86 题） | 每题执行输入 Token | 相对 all 的准确率差 [95% CI] | 输入变化 |
|---|---:|---:|---|---:|
| all | 98.8% | 45,220 | — | — |
| declared | 96.5% | 5,355 | −2.3 pp [−7.0, +2.3] | −88.2% |
| bm25 | 59.3% | 5,333 | −39.5 pp [−50.0, −29.1] | −88.2% |
| oracle | 97.7% | 16,030 | −1.2 pp [−4.7, +2.3] | −64.6% |

两个模型的结论一致：声明式装配输入少约 88%，准确率没有显著下降；同预算 BM25 显著下降。Qwen3.8 上广播全部候选准确率最高，所以“干扰项有害”只在 Qwen3.5 上出现，取决于模型，不能当一般结论讲。

## 四、实验 C：快照恢复对重试的影响

问题：任务失败后重试，从干净的私有上下文开始（快照恢复）和带着失败那次写入的私有段继续，哪个更好？

协议（服务器 `experiments/semantic_recovery/README.md`）：

- 沿用实验 A 的题，给出全部所需文档，不做检索。每题一个 agent：逐文档调用模型抽取签名事实，写成私有上下文段，最后一次调用作答。
- 第一次尝试必定注入故障，位置和类型由固定种子决定：一半题在写入 K 段后抛异常（执行失败），一半题在写入 K 段后追加一段错误事实，并把答案改成冻结的错误答案，由校验器判为语义失败。
- `dirty` 与 `snapshot` 只差 `restore_context`：都用同一个校验器、带反馈的 `SemanticRecoveryPolicy`、最多 2 次尝试。`no_retry` 只尝试 1 次，作为不恢复的基准。
- Qwen3.5-9B，关闭思考，温度 0，输出上限 4096，截断 0。按题配对 bootstrap 95% CI。

Qwen3.5-9B，100 道正式题：

| 组 | 准确率 | 调用数 | 输入 Token 合计 |
|---|---:|---:|---:|
| no_retry | 0% | 223 | 367,801 |
| dirty | 89% | 573 | 973,225 |
| snapshot | 87% | 573 | 931,647 |

snapshot − dirty：准确率 −2 个百分点 [−9, +5]；每题输入 −416 Token [−480, −356]，约 −4.3%。分层看，执行失败题 +4 个百分点 [−4, +12]，语义失败题 −8 个百分点 [−20, +2]，都不显著。50 道语义注入题全部被校验器发现。`dirty` 组有 2 道语义题的重试照抄了残留的错误事实（参数名就是注入的占位符），重复检测在第二次就停止；`snapshot` 组没有这种情况。

换模型复跑（Qwen3.8-27B，100 题）：no_retry 0%，dirty 96%，snapshot 88%。按协议的严格判分，snapshot − dirty 为 −8 个百分点 [−15, −2]，全部来自执行失败题。事后检查（未预先登记）发现差距全是格式问题：这些题的最终答案内容正确，只是包在 Markdown 代码块里，被严格判分拒绝；最终答案带代码块的，dirty 4 道、snapshot 12 道。去掉代码块后两组都是 100%。残留的私有段是裸 JSON，可能让模型跟着输出裸 JSON，这一点没有单独验证。校验反馈只说“未通过验收”、不指出格式，模型第二次仍带代码块。

解读与限制：

- 在答案内容上，快照恢复与保留残留没有可测的差别，输入只少 3%–4%。原因之一是失败尝试留下的私有段很短：`dirty` 重试开始时平均只有 1.7–2.8 段、约 340–565 字符，相对每题约 9–10k 的输入很小。
- 残留错误事实确实会被模型照抄（2/50），但发生率低，100 题的样本测不出准确率差异。反馈消息明确要求“重新读源码、核对私有事实”，也会削弱残留的影响。
- 要让这个对照有区分度，需要失败尝试留下大量或更有迷惑性的私有状态的任务（例如长工具输出、多轮推理草稿）。
- 准确率与完成率在本协议中一致，因为完成就是通过精确答案校验。
- Qwen3.8 的结果说明，校验反馈应当给出可操作的原因（例如“必须输出裸 JSON”），否则重试会重复同一个可修正的错误。

- 实验 B 的 Qwen3.5 第一次运行没关思考（默认思考 + 输出上限 512 会截断），中途停掉，加了 `--thinking-off` 后重跑。

## 六、对面试口径的影响

- 缓存亲和：可以讲“在 Runtime 主链上测过：KV 不足以容纳全部共享前缀时，完工时间降 33%–55%（批宽 4），充足时无收益”，并说明原自动策略因固定饥饿阈值在 LLM 负载下失效、已改为按服务时间缩放。
- 按需装配：旧的 44.5%／60.2% 输入降幅来自预设的角色规则，不能当 Runtime 能力讲；新结果是“模型声明所需文档、Runtime 按声明装配，输入少 88%，准确率不降；同预算检索掉 18 个百分点”，同时说明题面点名了符号。
- “Agent 错了怎么办”：现在有校验器、带反馈重试、快照恢复、重复检测和事件归因，可以按机制讲，并说明实测：注入故障后重试恢复到约九成；快照恢复在短残留任务上收益很小；反馈要给出可操作的原因。
- 这些都是赛后在个人副本上做的，不是比赛交付版本的能力。
